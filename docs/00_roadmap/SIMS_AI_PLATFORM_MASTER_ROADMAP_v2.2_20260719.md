## 0. 문서 개정 요약

이 문서는 기존 `SS AI Phase 3~7 실행 계획 및 체크 보고서`와 `SIMS AI Phase 3~8 실행 계획 및 체크 보고서 v2.0`을 기반으로, 새로 제안된 **AI Data Platform**, **Dashboard/Alert**, **Knowledge Center**, **Service AI** 방향을 반영한 최종본이다.

v2.2는 v2.1의 Phase 3~8 범위와 장기계획을 삭제하지 않고 모두 유지한다. 여기에 **사용자가 숫자를 그래프로 보고 바로 행동을 판단할 수 있는 Dashboard Lite를 먼저 보여준 뒤 피드백으로 구체화하는 방식**을 Phase 4 공식 실행전략으로 추가한다. 분석 숫자는 생산 코드가 확정한 facts만 사용하고, LLM은 상태·근거·행동을 설명하는 역할로 제한한다. 또한 현재 보유한 매입·매출·재고 자료로 계산 가능한 거래 회전일, 최근 거래 경과일, 재고커버일, 재고준비율을 우선 도입한다. 입금·출금·채권·채무 자료가 필요한 자금 회전지표는 후속 단계로 보류한다.

## 1. 방향 전환

기존 목표는 “ERP 조회에 AI를 붙이는 것”이었다. 그러나 v2.0부터는 목표를 다음과 같이 확장한다.

```text
SIMS ERP
+ AI Data Platform
+ ML 예측/추천
+ RAG / Knowledge Center
+ Dashboard / Alert
+ 업무지식 / 서비스지원 AI
= 의약품 유통업 전용 AI 플랫폼
```

즉, SIMS AI는 단순 조회형 챗봇이 아니라, 의약품 유통 ERP의 데이터를 이해하고, 검증하고, 예측하고, 업무를 안내하며, SIMS ERP 고객지원, 그룹웨어 업무지원, 교육까지 확장하는 **ERP AI Platform**을 목표로 한다.

### 1.1 v2.2 핵심 목표

| 목표 | 설명 |
|---|---|
| 정확한 조회 | SIMS ERP 원본과 일치하는 조회/집계 결과를 제공한다. |

| 업무지식 활용 | 업무규칙, 매뉴얼, 뉴스, 외부 API, 그룹웨어 문서를 RAG로 연결한다. |

| 행동 중심 안내 | 모든 핵심 화면에서 상태→근거→오늘 할 일을 함께 제공한다. |
| 고객지원 확장 | SIMS ERP 사용설명서, SIMS 문의, SIMS 장애, SIMS 설치, SIMS 교육, SIMS 개발자지원과 그룹웨어 업무지원을 AI로 지원한다. |

# Phase 3. 로그인 / 권한 / 회사별 DB

## 3.1 목적

여러 회사와 사용자가 SIMS AI를 안전하게 사용할 수 있도록 로그인, 권한, 회사별 DB 연결, 사용자별 저장소를 분리한다. Phase 3는 SIMS AI가 “개발자 단독 도구”에서 “운영형 ERP AI 서비스”로 전환되는 기반 단계다.

## 3.2 기능 설명

### 3.2.1 사용자 인증

사용자가 SIMS AI에 로그인한다. 관리자는 전체 기능을 사용할 수 있고, 도매 사용자, 회사 관리자, 읽기 전용 사용자 등은 역할과 권한에 따라 메뉴와 기능이 제한된다.

### 3.2.2 회사별 DB 선택

한 명의 사용자가 여러 회사 DB에 접근할 수 있다. 로그인 후 접근 가능한 회사만 표시하고, 선택한 회사의 ERP DB로 연결한다. 접근 권한이 없는 회사 DB는 조회할 수 없다.

### 3.2.3 권한 관리

사용자별로 다음 기능의 사용 가능 여부를 제어한다.

| 권한 영역 | 제어 대상 |
|---|---|
| 조회 권한 | SIMS 조회, Master 조회, IO 조회, 재고 조회 |
| KPI 권한 | 분석/KPI 화면, KPI NLQ, KPI 후속분석 |
| 다운로드 권한 | Excel/CSV 다운로드 |
| 업로드 권한 | 파일 업로드, 문서 분석 |
| 관리자 권한 | 사용자 승인, 회사 관리, 권한 관리 |
| 회사 DB 권한 | 회사별 ERP DB 접근 |

### 3.2.4 사용자별 채팅방 분리

사용자마다 채팅방과 조회 결과가 분리된다. 다른 사용자의 채팅방, current table, 다운로드 파일, 업로드 파일에 접근하지 못하게 한다.

### 3.2.5 회사 변경 시 캐시 초기화

회사 DB를 바꾸면 이전 회사의 조회 결과, current table, export cache를 초기화한다. 이 기준은 회사별 데이터 섞임을 막기 위한 필수 보안 기준이다.

# Phase 4. KPI / 분석 안정화

## 4.1 목적

현재 만들어진 분석/KPI를 정확하게 안정화하는 동시에, 사용자가 숫자를 이해하고 행동할 수 있는 1차 화면을 빠르게 제공한다. 완벽한 전체 설계를 기다리지 않고 **최소 검증 facts → Dashboard Lite v0.1 → 사용자 파일럿 → v0.2 → 전체 계약·회귀** 순서로 진행한다.

### 4.1.1 실행 원칙: Show First, Facts Backed

1. 숫자는 가능한 한 그래프와 상태표시로 보여준다.
2. 화면은 `지금 어떤가 → 왜 그런가 → 무엇을 해야 하나` 순서로 읽히게 한다.
3. 행동 규칙은 생산 코드가 확정한 facts와 임계값에서 생성한다.
4. LLM은 계산하거나 원인을 추측하지 않고 확정 facts를 쉬운 말로 설명한다.
5. v0.1을 빠르게 운영자에게 보여주고 피드백을 받아 v0.2에서 역할·예외·우선순위를 구체화한다.
6. 임계값과 계산식은 버전 관리하고, 클릭하면 기존 상세표에서 근거를 확인할 수 있게 한다.

### 4.1.2 Phase 4 세부 영역과 현재 상태

| 영역 | 내용 | 현재 상태 |
|---|---|---|
| Phase 4A | 현재표·이전표, 파생표, 렌더링, 다운로드, context 연결 안정화 | 완료 |

## 4.2 Dashboard Lite 목표 화면

Dashboard Lite는 새 분석 엔진을 한 번에 완성하는 작업이 아니라, 이미 확인한 매출추세·매출예상·재고부족 facts를 사용자가 즉시 이해하도록 재구성하는 1차 업무화면이다.

| 화면 영역 | 표시 내용 | 사용자가 판단할 내용 |
|---|---|---|
| 오늘의 업무 브리핑 | 정상·주의·경고·긴급 수, 전일 대비 변화 | 오늘 먼저 볼 문제 |
| 매출 그래프 | 완료월 추세, 당월 실제, 월말 예상, 상·하락 기여 | 목표 달성 가능성과 위험 업체·품목 |
| 매입 그래프 | 매입 추세, 거래일 간격, 최근 매입 경과 | 공급활동 중단·지연 후보 |
| 재고 그래프 | 재고준비율, SKU·금액 준비율, 재고커버일 | 부족·과다·예외 품목 |
| 오늘의 조치 | 우선순위가 높은 5~10건 | 담당자가 오늘 확인·연락·발주할 일 |
| 근거 상세 | 기존 상세표로 이동 | 계산 근거와 대상 행 검증 |

색상만으로 상태를 구분하지 않고 `정상·주의·경고·긴급` 라벨과 수치를 함께 표시한다. 사용자 역할에 따라 경영자에게는 요약·집중도·기여도를, 구매담당자에게는 부족수량·최근 매입·공급위험을, 영업담당자에게는 고객·제품별 위험과 조치를 우선 표시한다.

### 4.2.1 매입·매출 회전일의 1차 정의

현재 입금·출금, 매출채권, 매입채무 잔액 자료가 없으므로 DSO·DPO 같은 자금 회전일은 계산하지 않는다. Phase 4에서는 실제 보유한 거래자료로 다음 운영지표를 사용한다.

| 지표 | 1차 정의 | 집계·예외 |
|---|---|---|
| 매입 거래 회전일 | 조회기간의 서로 다른 매입일 사이 평균 간격 | 같은 날 여러 명세서는 1개 활동일; 반품일은 별도 표시 |
| 매출 거래 회전일 | 조회기간의 서로 다른 매출일 사이 평균 간격 | 같은 날 여러 명세서는 1개 활동일; 반품일은 별도 표시 |
| 최근 매입 경과일 | 기준일 - 가장 최근 정상 매입일 | 거래일 0~1개이면 자료부족 |
| 최근 매출 경과일 | 기준일 - 가장 최근 정상 매출일 | 거래일 0~1개이면 자료부족 |
| 재고커버일 | 현재 사용 가능 재고 ÷ 일평균 예상수요 | 예상수요 0이면 별도 상태 처리 |

비교기간은 최근 90일 또는 완료된 최근 3개월을 우선 사용한다. 미완료 당월의 거래일 수 때문에 평균 간격이 왜곡되지 않도록 부분월 포함 여부를 facts에 명시한다. 자금 회전일은 입금·출금·채권·채무 자료가 확보된 이후 별도 설계한다.

### 4.2.2 재고준비율과 98% 침묵 정책

```text
당월 잔여예상수요 = 당월 월말 예상수요 - 당월 현재 출고수요
준비가능수량 = min(max(현재 사용 가능 재고, 0), 당월 잔여예상수요)
재고준비율 = 준비가능수량 ÷ 당월 잔여예상수요 × 100
부족수량 = max(당월 잔여예상수요 - 현재 사용 가능 재고, 0)
```

당월 잔여예상수요가 0이면 준비율은 100%로 표시한다. 화면 표시값은 100%를 상한으로 하고, 안전재고·확정입고가 없는 v0.1에서는 현재 사용 가능 재고만 사용한다. 예를 들어 현재 사용 가능 재고 980개, 당월 잔여예상수요 1,000개이면 재고준비율은 98%, 부족수량은 20개다.

| 구간 | 상태 | 기본 처리 |
|---:|---|---|
| 99% 이상 | 정상 | 일반 부족 알림 없음 |
| 98% 이상~99% 미만 | 정상범위 | 일반 부족 알림 없음, 상세에서 확인 가능 |
| 95% 이상~98% 미만 | 주의 | 부족수량과 확인 조치 표시 |
| 90% 이상~95% 미만 | 경고 | 구매·영업 확인 대상에 포함 |
| 90% 미만 | 긴급 | 오늘의 조치 상단에 배치 |

98% 이상이면 영업사원에게 일반적인 재고부족 알림을 반복하지 않는다. 다만 핵심·고매출 품목 재고 0, 특별관리품목, 음수재고, 재고커버일이 통상 매입 회전일 또는 조달 리드타임보다 짧음, 장부·실재고 불일치, 급격한 수요증가는 예외 알림으로 유지한다. 알림은 98% 미만에서 시작하고 99% 이상 또는 2회 연속 정상 확인 후 해제하며, 더 나빠지거나 다음 날에도 미해결인 경우가 아니면 같은 내용을 반복하지 않는다.

### 4.2.3 v0.1 준비율 묶음

| 지표 | 정의 | 용도 |
|---|---|---|
| 수량 준비율 | 준비가능수량 합계 ÷ 잔여예상수요 합계 | 전체 수량 충족 가능성 |
| SKU 준비율 | 품목 준비율 98% 이상 SKU 수 ÷ 수요 발생 SKU 수 | 부족 영향을 받지 않는 품목 비율 |
| 금액 준비율 | 충족 가능한 예상 매출금액 ÷ 전체 잔여 예상 매출금액 | 매출가치 기준 위험 |

회사 전체 준비율만으로 정상 판단하지 않는다. 상위 매출품목, 핵심거래처, 재고 0, 음수재고 등 예외를 별도로 확인한다. 확정 발주·확정 입고 자료가 확보되면 구매 대응 준비율을 추가하고, 영업사원·거래처 준비율과 데이터 준비도·신뢰도를 v0.2 이후 확장한다.

### 4.2.4 결합 판단 규칙

- 준비율 98% 미만이면서 매출 거래 회전일이 짧거나 최근 판매가 급증하면 부족 위험 우선순위를 높인다.
- 매입 거래 회전일은 빨라지고 매출 거래 회전일은 느려지며 재고가 증가하면 과다재고 후보로 표시한다.
- 최근 매입 경과일이 통상 매입 거래 회전일보다 길고 준비율도 낮으면 공급처·발주 지연 확인을 제안한다.
- 업체 수만으로 전체 흐름을 판단하지 않고 매출 비중, 증감 금액, 성장·감소 기여도를 함께 사용한다.
- 원인 자료가 없으면 원인을 단정하지 않고 `확인 필요` 조치로 표현한다.

## 4.4 기능 설명

### 4.4.1 화면 표시 row 제한

대량 데이터 전체를 화면에 표시하지 않는다. 화면은 `.env` 제한값을 따르되, 전체 집계와 다운로드는 원본 전체 기준으로 유지한다.

```text
화면 표시: display_rows 기준
집계/summary/download: full_rows 기준
```

### 4.4.2 전체 기준 summary 유지

LLM이 일부 화면표시 데이터만 보고 답하지 않도록, 전체 DataFrame 기준 요약값을 별도 생성한다. 특히 KPI에서는 현재 조회대상 분포와 전체 분포를 구분해야 한다.

### 4.4.3 Arrow 타입 보정

Streamlit 표 렌더링 시 mixed object 컬럼 때문에 발생하는 PyArrow 오류를 방지한다. 날짜/숫자/문자열 혼합 컬럼은 표시 전 타입을 안정화한다.

### 4.4.4 다중 조건 조회

제품구분명, 제품분류명, 재고위치, 제조사, 거래처, 영업사원 등 조건을 다중 선택할 수 있게 한다.

### 4.4.5 KPI 결과 검증

KPI 결과가 ERP 원본 기준과 맞는지 다음 기준으로 검증한다.

| 금액 | 공급가액, 세액, 합계금액 |
| 월별 합계 | 월 단위 집계 일치 여부 |

```text
→ SQL/서비스 결과
→ full DataFrame
→ 화면 KPI/meta
→ summary_md/llm_summary_md
→ SIMS analysis context
→ analysis profile
→ 최종 LLM prompt
```

08A-Quick에서는 소스, 테스트, SQL, DB를 수정하지 않는다. prompt만 임시로 확대하지 않으며 `git add`, commit, push도 수행하지 않는다. 전체 전수조사의 틀은 유지하되 Dashboard Lite v0.1에 필요한 핵심 화면과 지표를 먼저 확정하고, 나머지 action은 08F 전체 계약에서 완결한다.

반드시 확정할 내용은 다음과 같다.

- 완료월 총매출의 정의와 완료월 합계·월평균 구분
- 당월 현재매출과 완료월 지표의 집계 범위
- 당월 예상매출 계산식
- 당월 진척률의 분자와 분모
- 추세판정 기간과 판정 기준
- 제약사 수와 월별 행 수의 차이
- 추세판정 건수가 업체별 최종 판정인지 월별 중복인지
- 상세표 348개와 요약표 11개의 차이와 선정 기준
- 업체 수와 매출액·매출 비중의 관계
- 부분월과 완료월의 직접 비교 가능 여부
- LLM이 앞 30행 sample에 의존하는지 여부
- 화면 KPI, Excel, meta, `llm_summary_md`의 숫자 일치 여부

Dashboard Lite의 각 fact에는 `status`, `threshold_version`, `action_code`, `action_text`, `exception_reason`, `drilldown_table_key`를 추가할 수 있다. 임계값 변경 이력과 사용자 피드백은 facts 계산식과 분리해 관리한다.

### 공통 오판 방지 정책

1. 집계 기준이 다른 KPI끼리 직접 비교하지 않는다.
2. 부분월 실제와 완료월 실적을 단순 비교하지 않는다.
3. 업체 수만으로 전체 매출 흐름을 판단하지 않는다.
4. 추세판정 수와 추세판정별 매출액을 함께 사용한다.
5. 매출 비중과 증감 기여도를 함께 사용한다.
6. 예상값과 실제값을 명확히 구분한다.
7. 원인 데이터가 없으면 원인을 단정하지 않는다.
8. sample records만으로 전체 합계·순위·비중을 판단하지 않는다.
9. 자료부족과 데이터 완전성을 명시한다.
10. 합계·평균·고유개수·상세행 수를 구분한다.
11. 회전일은 거래 회전일과 자금 회전일을 혼용하지 않는다.
12. 회사 전체 준비율이 정상이어도 핵심품목·재고 0·음수재고 예외를 숨기지 않는다.
13. 동일 경고는 악화·익일 미해결·예외 발생이 아니면 반복하지 않는다.
14. 사용자의 조치 완료·도움 됨·불필요 알림 피드백을 다음 기준 보정에 사용한다.

# Phase 4.5. AI Data Platform

## 4.5.1 목적

ML, RAG, Dashboard, Alert가 공통으로 사용할 AI 전용 데이터 기반을 만든다. ERP 원본 DB를 직접 매번 계산하는 구조에서 벗어나, AI 분석용 검증/집계/통계/Feature 데이터를 구축한다.

## 5-1. 매출예상 ML

### 기능 설명

제품별, 거래처별, 영업사원별 매출을 예측한다.

기존 Rule 방식은 다음과 같다.

| 방식 | 설명 |
|---|---|
| 이동평균 | 최근 기간 평균으로 예측 |
| 최근 3개월 평균 | 단기 수요 기준 |
| 최근 6개월 평균 | 안정 수요 기준 |
| 전년동월 기준 | 계절성 반영 |
| 증감률 기준 | 최근 증가/감소 추세 반영 |

ML 방식은 다음을 검토한다.

| 모델 | 목적 |
|---|---|
| RandomForest | 초기 기준 모델, 중요 변수 확인 |
| XGBoost | 고성능 tabular 예측 후보 |
| LightGBM | 대용량 데이터 예측 후보 |
| LSTM | 장기 시계열 후보, 운영 부담 검토 필요 |

### 평가 기준

| 지표 | 설명 |
|---|---|
| MAE | 평균 절대 오차 |
| RMSE | 큰 오차에 민감한 지표 |
| MAPE | 실제 대비 오차율 |
| 방향성 적중률 | 증가/감소 방향 예측 성공률 |
| 제품별 정확도 | 제품별 예측 품질 |
| 거래처별 정확도 | 거래처별 예측 품질 |

# Phase 7. LoRA / Agent / Workflow

## 7.1 목적

SIMS AI를 업무 특화 모델과 자동 업무 수행 Agent로 발전시킨다. Phase 7은 단순히 모델을 학습시키는 단계가 아니라, 사용자의 반복 업무 흐름을 AI가 단계적으로 수행하게 만드는 고도화 단계다.

---

## 7-1. LoRA / QLoRA

### 기능 설명

SIMS ERP 질문/답변, 업무 규칙, 실패 사례를 학습시켜 모델이 SIMS 업무 표현과 패턴에 익숙해지게 한다.

### 목적

RAG만으로 부족한 말투, 업무 흐름, 질문 해석 능력을 개선한다.

### 학습 후보 데이터

| 데이터 | 설명 |
|---|---|
| NLQ 성공 사례 | 질문 -> action/조건/답변 |
| NLQ 실패 사례 | 실패 질문 -> 원인 -> 수정 답변 |
| 현재표 후속질문 | 현재표 schema + 질문 -> 분석 답변 |
| 업무 Q&A | 업무규칙 기반 질문/답변 |
| 장애 대응 Q&A | 로그/오류 -> 원인/조치 |

| Workflow | 설명 |
|---|---|
| 매일 아침 매출 브리핑 | 오늘/전일/월누계 매출 요약 |

## 7-4. AI Agent

### 기능 설명

AI가 여러 단계를 스스로 수행한다.

예시는 다음과 같다.

```text
재고부족 찾아줘
→ 조회
→ 분석
→ 발주추천
→ 보고서 작성
→ 메일 초안 작성
```

Agent는 반드시 권한, 회사, 데이터 범위, 실행 로그를 확인해야 한다. 실제 DB 변경 작업은 초기에는 허용하지 않고 조회/분석/보고서 초안 생성부터 시작한다.

# Phase 8. SIMS ERP & Groupware Service AI

## 8.1 목적

SIMS ERP 프로그램인 **SIMS**의 운영, 고객지원, 교육, 설치지원과 회사 내부 **그룹웨어 업무지원**까지 AI 서비스로 확장한다. Phase 8은 SIMS AI를 내부 분석 도구에서 SIMS 고객지원, 그룹웨어 업무지원, 상용 서비스로 확장하는 단계다.

---

## 8-1. SIMS ERP 사용설명서 AI

### 기능 설명

사용자가 ERP 사용법을 질문하면 메뉴 위치, 입력 방법, 주의사항을 안내한다.

예시는 다음과 같다.

| 질문 | 답변 방향 |
|---|---|
| 입고등록은 어떻게 하나요? | 메뉴 위치, 입력 순서, 필수값 안내 |
| 거래명세서는 어디서 출력하나요? | 출력 메뉴, 조건, 재출력 주의사항 안내 |
| 제품코드는 어떻게 등록하나요? | 제품등록 화면, 필수코드, 보험코드 안내 |
| 세금계산서 검증은 어떻게 하나요? | 조회 조건, 검증 기준, 불일치 처리 안내 |

---

## 8-2. SIMS 문의사항 처리 AI

### 기능 설명

SIMS ERP 고객 문의를 자동 분류하고 관련 FAQ와 조치 방법을 추천한다. 문의 대상은 일반 ERP 문의가 아니라 **SIMS 프로그램 사용법, SIMS 데이터 조회, SIMS 오류, SIMS 설치, SIMS 개선 요청**으로 명확히 구분한다.

| 분류 | 예시 |
|---|---|
| SIMS 사용법 문의 | SIMS 메뉴 위치, 입력 방법, 출력 방법 |
| SIMS 데이터 문의 | SIMS 조회 결과 불일치, 금액 차이, 재고/매출 기준 |
| SIMS 오류 문의 | SIMS 실행 오류, 접속 오류, 조회 오류 |
| SIMS 설치 문의 | ODBC, SQL Server, Streamlit, LM Studio, 회사 DB 연결 |
| SIMS 개선 요청 | SIMS 화면/기능/NLQ/보고서 추가 요청 |
| 그룹웨어 문의 | 공지, 업무지시, 결재 문서, 사내 규정 검색 |

---

## 8-3. SIMS 장애 대응 AI

### 기능 설명

SIMS 오류 메시지, 로그, 화면 증상, DB 접속 상태를 기반으로 원인과 조치 방법을 안내한다. 그룹웨어 연동 오류가 있는 경우에는 그룹웨어 문서/공지/결재 연동 상태도 함께 확인한다.

예시는 다음과 같다.

| 증상 | 확인 방향 |
|---|---|
| Streamlit 접속 불가 | 8501 포트, config.toml, 방화벽 확인 |
| LM Studio 응답 없음 | Serve ON, 1234 포트, 모델 로딩 확인 |
| SQL 접속 오류 | ODBC, DB 계정, 회사 DB 접속정보 확인 |
| Invalid column name | schema_map/labels_map/SQL 필드 확인 |
| PyArrow 오류 | 표시 DataFrame 타입 보정 확인 |

# 9. 공통 운영 원칙

## 9.1 정확성 우선

빠른 결과보다 ERP와 일치하는 정확한 결과를 우선한다. AI 집계DB, ML, RAG가 추가되어도 ERP 원본 기준과 검증되어야 한다.

## 9.2 전체 기준 유지

화면 표시 row는 제한할 수 있으나, 집계/summary/다운로드/ML 학습은 전체 기준을 유지한다.

```text
화면 표시: 제한 가능
분석/집계: 전체 기준
다운로드: 전체 기준
ML 학습: 전체 기준
검증: ERP 원본 기준
```

## 9.3 출처 표시

RAG, 뉴스, 외부 API 답변은 기준일과 출처를 표시한다. 출처가 불명확하거나 오래된 문서는 답변에 주의 문구를 표시한다.

## 9.4 권한 분리

회사별, 사용자별, 역할별 데이터 접근 권한을 반드시 적용한다. 특히 RAG 문서, 다운로드 파일, current table, export cache는 user_id/company_id 기준으로 격리한다.

## 9.5 GitHub 기준 운영

1호기 개발, GitHub push, 2호기 pull 방식으로 운영한다. 단, `git commit`만으로 2호기에 자동 적용되는 것은 아니므로 2호기 반영 절차를 반드시 수행한다.

## 9.6 배포 전 회귀 테스트 필수

배포 전에는 현재 프로젝트 가상환경을 사용하여 Master, Analytics/KPI, IO, 전체 회귀를 확인한다. 2호기 기준 Python 실행은 `& .\.venv\Scripts\python.exe`이며, `.env`는 가상환경이 아니라 환경설정 파일이다. 실제 명령과 옵션은 저장소의 최신 회귀 실행기를 기준으로 한다.

```powershell
cd C:\New\Python_Project\LmStudion_project1

& .\.venv\Scripts\python.exe tools\check_master_nlq_regression.py --live
& .\.venv\Scripts\python.exe tools\check_analytics_regression.py --live --nlq
& .\.venv\Scripts\python.exe tools\check_io_nlq_regression.py --live-all
& .\.venv\Scripts\python.exe tools\check_all_regression.py --quick
```

현재 공식 자동 회귀 기준선은 `총 90건 / 성공 90건 / 실패 0건`이다. 새 회귀가 추가되면 총건수도 함께 갱신한다.

## 9.7 분석 의미와 provenance 우선

분석/KPI의 LLM 답변은 raw sample의 임의 계산보다 생산 코드가 확정한 facts를 우선한다. 각 지표의 합계·평균·고유개수·grain·시간 기준·부분월·예상 여부·비교 가능성을 함께 전달하고 검증한다.

## 9.8 모델 관리 권한 분리

사이드바의 모델 관리 UI와 모델 목록 조회는 플랫폼 최고관리자에게만 허용한다. 회원사 사용자·관리자와 일반 플랫폼 관리 역할은 모델 운영 정보에 접근하지 못하게 하며, 일반 completion 실패는 안전한 사용자 메시지로 변환한다.

# 12. 최종 판단

이번 v2.2의 핵심은 다음 한 문장으로 정리할 수 있다.

> SIMS AI는 검증된 숫자를 그래프로 먼저 보여주고, 왜 그런지와 오늘 무엇을 해야 하는지를 안내하며, 사용자 피드백으로 단계적으로 정교해지는 의약품 유통 AI Platform으로 확장한다.

따라서 당장 다음 작업은 전체 플랫폼 설계가 끝날 때까지 기다리는 것이 아니라, 핵심 facts를 확인한 Dashboard Lite v0.1을 빠르게 보여주고 사용자 반응을 받은 뒤 전체 정확성 계약과 AI Data Platform 기반으로 확장하는 것이다.

**최종 우선순위는 다음과 같다.**

1. Phase 3 운영 유지: 완료된 로그인·권한·회사별 DB·사용자별 저장소 분리를 회귀로 보호한다.
2. Phase 4B: 핵심 facts, 거래 회전일, 재고준비율과 98% 침묵 정책을 확정하고 Dashboard Lite v0.1을 구현한다.
3. Phase 4C: 사용자 파일럿과 v0.2 후 전체 Analytics Facts, profile, LLM 설명을 완결한다.
4. Phase 4 마감: 09 입출고명세 의미 보정과 10 성능 최적화를 완료한다.
5. Phase 4.5 설계·구축: Validation Framework, AI 집계DB, 통계DB, Feature Store, KPI Library.
6. Phase 5 착수: ML 매출예상·재고부족·발주추천·AI Score.
7. Phase 6 확장: 업무지식, 그룹웨어, 심평원 API, 뉴스·제도 자료 RAG.
8. Phase 7 고도화: LoRA, Agent, Workflow, Feedback Learning.
9. Phase 8 서비스화: SIMS 사용설명서, 문의, 장애, 설치, 교육, 개발자지원, 그룹웨어 업무지원 AI.
