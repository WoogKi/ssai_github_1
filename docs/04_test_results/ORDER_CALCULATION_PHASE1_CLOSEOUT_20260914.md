- 계산/추천/실제 초기수량 분리, 정수 추천, 최소 발주단위, 실제수량 편집과 금액·다운로드 연결을 마감했다.

## 4. 가격 NULL 원인과 수정

83315와 23976은 유효한 50002 계약이 존재했지만 NLQ 일반 조회기간이 계약단가 SELECT의
계약시작일 범위로 누출됐다. 83315의 계약 시작일은 2025-12-29, 23976은 2015-10-30으로
자동 조회기간 밖이라 제외됐다. 이후 83315는 복수 최종매입가, 23976은 매입가 부재/등록단가 0으로 NULL이 됐다.

발주 service의 계약단가 파라미터 경계에서 일반 기간을 제외하고 기준일 유효성을 유지했다.
R070 SQL·가격 우선순위·VAT·source budget은 변경하지 않았다. 두 제품의 직접 UI service와
production NLQ, 전체/해당 가격·수량·금액이 일치했다. 당시 수정 전후 NLQ source_call_count는
두 제품 모두 10이었다. 실제 계약단가 복구를 임의 fallback 보정과 구분한다.

## 5. 검증과 남은 관찰

- 발주 계산 focused 28/28, NLQ·제조사 충돌·기존 발주조회, 전체 analytics regression PASS.
- editor/금액/current-table/full export, Excel numeric/code/null 회귀 PASS.
- `py_compile`, `pip check`, `git diff --check` PASS.
- 사용자 보고 기준 Snapshot HY000은 1회 관찰 후 이후 미재현이다. 해결 완료로 단정하지 않으며
  재발 시 단계·SQLSTATE·elapsed를 별도 진단한다. 발주 본체와 섞어 수정하지 않는다.
- 현재 authoritative 매입거래처수는 없어 빈값을 유지한다. 자료부족을 임의 0이나 추정값으로 만들지 않는다.
- 실제 ERP 발주 등록/확정, 자동발주, 실제수량 단위배수 강제, 정산 반올림은 1차 범위 밖이다.
- 키보드 연속 입력은 사용자 브라우저/Streamlit widget 동작의 운영 관찰 항목이며 별도 component나 hack을 도입하지 않는다.
- Knowledge/RAG 문서 세트 준비와 운영 corpus 승인/등록은 별개다. 이번 문서 작업에서 실제 등록하지 않는다.
