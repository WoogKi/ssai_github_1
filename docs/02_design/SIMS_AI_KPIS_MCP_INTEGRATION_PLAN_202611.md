# KPIS 의약품정보센터 OpenAPI·MCP 연동 개발계획

**지위:** [공식 로드맵 v2.5](../00_roadmap/SIMS_AI_PLATFORM_MASTER_ROADMAP_v2.5_20261027.md)의 Phase 4.x 독립 Tool/MCP 공식 개발계획(PX-10, P6-08, S03-07). 실제 외부 API 접근·인증정보 저장·DB Migration·배포 승인은 별개다. [기존 MCP 현황](SIMS_AI_MCP_CURRENT_STATE_AND_NEXT_PHASE_20261027.md)의 Mock/로컬 STDIO PoC를 재사용한다. 외부 KPIS 연결·LM Studio Native MCP·운영 권한 배포는 아직 완료 근거가 없다.

**가이드 근거:** 로컬 `3.OpenAPI개발가이드_통합.pdf`(표지 2026-03-30)에서 MA101/MA109/MA117/MA118과 MA111/MA113의 분류를 읽기 전용 확인했다. 시험 인증키/JWT 예시는 실제 자격증명으로 간주하지 않고 이 문서/소스/로그에 복사하지 않는다. 실제 endpoint·약관·인증방식·응답 필드/호출 제한은 개발 착수 때 공식 최신 사양을 재확인한다.

## 우선순위와 경계

| 순서 | API | 읽기 사용 목적 | 1차 범위 |
| --- | --- | --- | --- |
| 1 | MA117 | 의약품센터 공지사항 조회, 공식 출처/게시·조회시각 표시 | 승인된 작은 read-only PoC |
| 2 | MA109 | 회수의약품 정보 조회; 회수 정보의 기준일·식별자 검증 | 동일 권한/격리 Gate 통과 뒤 추가 |
| 3 | MA101 | 표준코드 마스터 단건·조건 조회, 제품코드 문자열 유지 | 코드 일치/미일치/다의성 검증 뒤 추가 |
| 이후 | MA118 | 전체 표준코드 범위/용량·갱신 정책 검토 | 대량 수집·운영 캐시 별도 승인 |
| 이후 | Rddbc040/Rddbc046 연계 | ERP 제품코드와 외부 표준코드 매핑 계약 조사 | 매핑 근거·회사 권한 Exact 전 자동 결합 금지 |

MA111·MA113 등 외부 데이터 변경 API는 1차 대상에서 제외한다. 기존 날짜·시간 Tool과 Brave Search API는 변경하지 않는다. KPIS 결과는 ERP 사실/Knowledge 승인 문서처럼 자동 승격하지 않는다.

## 최소 구조

`SIMS AI 명시 요청 → 서버 측 MCP_EXTERNAL_RESOURCE_READ·회사/사용자 검사 → MCP Adapter/Resource Allowlist → KPIS 전용 읽기 REST Client 또는 로컬 MCP Server → KPIS OpenAPI`.

- 기존 `/mcp-resource` 명시 경로와 Mock/STDIO Gate를 재사용한다. 현재 Adapter는 remote transport를 제공하지 않으므로 실제 REST 호출과 응답 DTO는 신규 격리 코드/서버가 필요하다. LM Studio Native tool-call 전환은 이 최소 PoC의 선행조건이 아니다.
- 기본 OFF, 승인 Resource별 최소 파라미터, 1회 물리 호출, timeout, 자동 재시도 0회, 실패 시 다른 업무 도구 자동 전환 0회를 유지한다. 모델이 API나 자격증명을 임의 선택하지 못하게 한다.
- 인증정보는 승인된 비밀 저장소/환경 주입으로만 사용하며 로그·화면·문서에 남기지 않는다. outbound 네트워크/서버 신원, KPIS 이용약관·쿼터, 개인정보 포함 여부, 회사별 자료와 외부 결과 결합 권한을 별도 승인받는다.
- 응답은 schema·코드/날짜·페이지·빈값을 검증하고 공식 출처, 조회시각(KST와 원본 시각 구분), 요청 대상, 실패/오래된 정보 경고를 남긴다. 비확인 회수/공지 상태는 확정 업무 판단에 사용하지 않는다. 감사에는 민감 원문/키 없이 요청 종류·회사·권한 결과·호출수·지연·출처 ID만 기록한다.

## 운영회사별 인증정보 관리 설계 후보

각 운영회사가 KPIS 이용 승인을 받고 자격증명을 발급받는 것을 원칙으로 한다. 현행 `ssai_auth_service.connect_ssai_db()`의 `SSAI_COMPANIES` 회사 식별, `ssai_admin.py`/`ssai_company_admin.py`의 관리자 화면, `ssai_permission_policy.py`의 권한 및 기존 감사 서비스를 **연결 후보**로 사용한다. `ssai_company_admin_service.py`에는 ERP DB 비밀번호용 Fernet 저장이 있으나, KPIS 키에 동일 암호화 키·테이블·복호화 권한을 재사용해도 된다는 뜻은 아니다. 별도 키 수명/회전과 복구 가능성을 승인받아야 한다. `ssai_storage_service.py`의 회사별 파일 경로는 비밀 저장소로 가정하지 않는다.

논리 후보 `SSAI_KPIS_CREDENTIAL`은 ERP/Analytics DB가 아닌 기존 SSAI 회사 등록 관리 경계에 두는 안을 우선 검토한다. 실제 DB 위치·테이블명·Migration은 설계 승인 후 결정하며 이번에 만들지 않는다.

| 필드 후보 | 의미·제약 |
| --- | --- |
| `credential_id`, `company_id` | 불변 ID와 `SSAI_COMPANIES.company_id` 참조. 조회/쓰기마다 선택 회사와 로그인 권한 재검증 |
| `applicant_business_no`, `provider`, `approval_reference` | API 신청 사업자번호(표시 시 마스킹), 제공자 및 실제 이용 승인 근거. 사업자번호만으로 타 회사 사용 허용 금지 |
| `auth_profile`, `auth_method`, `approved_services` | 회사 내 인증 프로필/발급 단위, API KEY·Client ID/Secret·JWT 발급 방식, 승인된 MA 코드 범위. 서비스별 자격증명이 다를 때만 별도 프로필; 같은 비밀은 중복 저장하지 않음 |
| `secret_ref` 또는 `encrypted_credential`, `key_version` | 보안 저장소 참조 우선 또는 승인된 키로 암호화한 값. 키는 DB 데이터와 분리. 원문/마스킹 해제 값 조회 API 없음 |
| `enabled`, `connection_status`, `last_checked_at` | 등록/사용·실제 연결 상태 분리. 확인시각과 오류 분류만 저장하고 원 응답·키는 저장 금지 |
| `created_at`, `updated_at`, `revoked_at`, `changed_by` | 등록·변경·폐기 및 변경 사용자. 실제 작업 감사는 기존 감사 경로와 연계하고 비밀을 `details`에 싣지 않음 |

승인 서비스 범위가 단일 컬럼으로 정확히 관리되지 않으면 별도 **서비스 범위 매핑**을 최소 추가하는 안을 검토한다. API별 독립 발급 시 별도 프로필을 허용하되 동일 키/Secret의 사본을 MA 코드마다 만들지 않는다. 활성 자격증명은 회사·발급 프로필·버전에서 하나만 선택되게 하고, 갱신은 버전 교체/폐기 시각과 감사가 남도록 설계한다. JWT를 고정 API KEY처럼 영구 저장하지 않는다. JWT 방식이 실제 필요한 서비스에서는 승인된 Client 자격증명으로 발급·만료·갱신하고, 단기 토큰은 메모리/승인된 일시 저장소에서만 보관하며 재발급 실패와 clock skew를 검증한다. MA별 실제 인증 방식은 최신 공식 가이드와 발급 내역으로 확인한다.

운영회사 관리자는 기존 관리자 메뉴의 회사 경계 안에서 **자기 회사** 이용현황, 승인 서비스·상태, 최종 연결 확인일, 등록/교체/비활성화, 마스킹된 식별자, 감사이력만 본다. 비밀 등록·변경은 재입력 방식이며 저장된 원문을 되돌려 표시하지 않는다. 별도 `KPIS_CREDENTIAL_MANAGE` 같은 전용 관리 권한은 **설계 후보**이고, 단지 `COMPANY_MANAGE` 또는 `MCP_EXTERNAL_RESOURCE_READ`가 있다는 이유만으로 비밀 수정 권한을 부여하지 않는다. 서버 측에서도 사용자·선택 회사·대상 회사·API 서비스 범위를 확인한다. 최고 관리자 예외가 필요하면 별도 감사/승인을 둔다. 회사 전환 시 폼·세션 캐시·연결 결과를 지워 타 회사 정보 재표시를 차단한다.

연결 확인은 명시적 클릭과 별도 승인된 읽기 전용 MA 호출 1회로 제한하고, 개발환경에서는 운영 자격증명을 사용한 HTTP 호출을 금지한다. UI에는 성공/실패, 시각, 비밀 아닌 오류 분류만 표시한다. 평문 DB 저장, 암호화 키와 데이터 동거, 로그/오류/화면/Git 유출, 무단 키 재사용을 금지한다. 변경·폐기·재발급 절차와 비활성화 직후 호출 차단, 키 교체 중 중복 사용/경합, 비밀 백업·복구 권한을 Gate로 둔다. 가이드의 시험 키/JWT는 운영 자격증명으로 쓰지 않는다.

## 개발 단계와 완료 Gate

| 단계 | 제안 시기 | 결과·완료 기준 |
| --- | --- | --- |
| K1 인증·권한·저장소 조사 및 테이블 설계 | 11/1~7, 월마감 안정 후 | 회사/서비스별 발급 계약, 비밀 저장·키 회전·감사/권한 설계 승인. DB 생성 없음 |
| K2 관리자 UI 설계 | 11/1~7 | 회사별 목록/등록/교체/폐기/마스킹/연결 확인 흐름과 서버 측 권한·회사 전환 Gate 확정 |
| K3 격리 MA117 PoC | 11/9~20, 외부 접속 별도 승인 시 | 기존 Adapter·Mock/STDIO와 독립 REST Client의 read-only 1회 호출; 출처·조회시각·timeout/retry0·비밀 비노출. **운영회사 관리 기능 완료 아님** |
| K4 인증정보 관리 구현 | 11/23~12월, 설계·DB 변경 별도 승인 시 | 회사별 등록/변경/비활성화, 암호화/참조, 감사·권한·마스킹·교체/폐기 테스트. 운영 DB Migration은 별도 승인 |
| K5 MA109·MA101 및 회사별 확인 | K4 이후 별도 승인 | 서비스별 발급 범위·실제 인증·연결 상태 및 회사 격리 확인; MA118은 별도 |
| K6 1호기/2호기 | K3~K5 Exact·보안 Gate 후 | 1호기 실제 수동 검증; 2호기 적용은 별도 승인/배포/Smoke |

K3의 외부 PoC 성공과 K4~K6의 운영 기능 완성을 혼동하지 않는다. 월마감·ML 정확성 검증과 작업/DB 부하가 충돌하면 KPIS 일정을 조정한다. 인증 스키마·UI·권한의 실제 구현은 이 문서만으로 승인되지 않는다.

**남은 위험:** 최신 API 사양/이용권·인증·호출 제한 미확인, 외부 표준코드와 ERP 제품코드의 매핑 다의성, 외부 데이터 최신성과 회수정보의 업무상 책임 범위. 공식 API 연결 성공을 제품 단위 Exact 매핑이나 운영 사용 승인으로 간주하지 않는다.
