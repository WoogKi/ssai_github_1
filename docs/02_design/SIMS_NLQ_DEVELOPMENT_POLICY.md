# SIMS NLQ 개발 원칙

이 문서는 NLQ의 업무 선택, 조건 해석, 실행 및 안내에 적용하는 공통 계약이다. 새 업무나 별칭을 등록하는 문서는 아니다. 업무별 기간, 재고, 권한 및 결과표 계약은 해당 기존 문서를 계속 따른다.

## 업무와 조건

1. 실행 업무는 현재 Registry에 등록되고 해당 사용자에게 허용된 canonical Action으로 확정한다. 명시적인 새 업무 요청은 이전 결과표의 후속분석보다 우선한다. 명확한 현재표 후속분석은 현재 회사의 표만 사용한다.
2. 업무명과 조회조건을 분리한다. 등록된 동의어·약칭은 해당 업무 계약 안에서 동일한 조건으로 해석하며, 조건이 업무명 앞뒤 어디에 있든 최종 파라미터가 같아야 한다. 단어가 비슷하다는 이유만으로 별칭을 추정하거나 업무 의미를 바꾸지 않는다. 예를 들어 매출예산과 매출 예상은 별개다.
3. 사용자가 명시한 조건은 실행 파라미터와 서비스 적용 범위까지 보존한다. 지원하지 않거나 해석하지 못한 조건을 제거하고 기본값 또는 전체 범위로 조회하지 않는다. 기본값은 해당 조건이 실제로 생략됐을 때만 적용한다. 명시 날짜와 기본 기간의 우선순위는 [기간정책](SIMS_AI_NLQ_기간정책_공식기준.md)을 따른다.
4. 최종 업무, 조건, 권한 및 회사 범위를 서비스 호출 전에 검증한다. 미등록 업무, 미확정 조건, 미지원 복합질문 또는 권한 없는 요청은 ERP 호출 0회로 중단한다. 지원 여부가 불명확하면 임의의 다른 업무를 실행하지 않는다.

## 안내와 결과

5. 미등록 업무나 불명확한 요청은 기존 SIMS 도움말을 통해 확인된 의미, 중단 이유와 지원되는 질문 방법을 안내한다. 추천 예문은 Registry, 파서, 조건 및 권한으로 재검증한 경우에만 제시한다. 예문에 없는 조건을 추가하거나 기존 조건을 빼지 않는다.
6. 안내, 조회조건 설명, 결과 상태, 집계 및 다운로드는 실제 실행된 Action과 최종 파라미터를 기준으로 일치해야 한다. 조회가 중단되었으면 실행하지 않았음을 명시한다. LLM은 확정된 표와 숫자를 설명할 수 있으나 업무 재선택, 조건 변경 또는 임의 재조회는 하지 않는다.
7. 회사·사용자 권한과 현재표 격리를 유지한다. 회사 변경 시 이전 회사의 현재표, 분석 Context, 내보내기 캐시 및 잔존 payload를 재사용하지 않는다. 표시 행과 허용된 전체 다운로드의 범위는 각각의 기존 계약을 따른다.

## 변경 검증

- 원문, canonical Action, 정규화 조건, 최종 서비스 파라미터, 실제 적용 필터, 결과/안내 및 ERP source-call 수를 함께 비교한다. 정상 질문의 기본값과 명시 조건을 모두 검사하고, 실패 질문은 ERP 호출 0회를 확인한다.
- Registry/Parser/Help 중 하나를 변경하면 해당 업무와 인접 업무의 Offline 회귀를 실행한다. Golden 사례의 구조 감사, Mock 실행, 실DB 조회, 브라우저 확인을 서로 다른 증거로 기록한다. 정적 감사 PASS를 실제 실행 PASS로 보고하지 않는다.
- 사례집 원문과 기대 Action을 테스트 통과 목적으로 임의 변경하지 않는다. 현재 저장소에는 `docs/NLQ 정리 20260807.xlsx`(227행)과 `docs/NLQ 정리 20261007.xlsx`(249행)가 있으며, GFINAL-248은 별도 실행 기준이다. 어느 기준을 사용하는지 파일·버전·체크섬으로 고정하고 결과를 합산하지 않는다.

## 기존 계약과의 관계

- Action/권한의 실행 기준은 `app/sims/nlq/action_inventory.py`와 업무별 Registry/Handler이다. 도움말 예문은 `app/ui/knowledge_chat_adapter.py`의 검증 경로를 따른다.
- [현재고·현재표 계약](SIMS_NLQ_CURRENT_STOCK_CURRENT_TABLE_CONTRACT.md), [기간정책](SIMS_AI_NLQ_기간정책_공식기준.md), 업무별 저장조건과 기존 테스트는 이 문서가 대체하지 않는다. 충돌이 발견되면 실행 계약을 임의로 바꾸지 말고 사례와 영향 범위를 보고한다.
