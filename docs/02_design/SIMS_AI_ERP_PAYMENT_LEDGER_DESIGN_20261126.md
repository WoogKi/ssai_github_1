## 1. 목적 및 범위
기존 SIMS의 업무 규칙을 보존하며 조회·NLQ·현재표·다운로드·분석을 확장한다. ERP 등록/수정/삭제, 자동 회계전표 생성은 제외한다. 기존 공통 기능을 재사용하며 신규 집계 테이블이나 Snapshot은 초기 범위에 포함하지 않는다.

## 3. 확정 업무 규칙
- 동일 거래처코드에 매입과 매출이 동시에 발생하지 않는다. 매입처·매출처 잔액 독립 계산. 거래처 코드 범위는 기존 계약과 특수 거래처를 확인하고 임의 변경하지 않는다.
- Gcode 0023의 입출금구분은 숫자로 보이더라도 문자형 식별자다. 원장 SQL과 동일하게 코드 < '50'은 입금, 코드 >= '50'은 출금이다. 선행 0과 영문을 유지하며 정수 변환이나 개별 카드코드 목록을 사용하지 않는다. 00/50은 매출/매입 발생이며 실제 현금 이동이 아니다.
- Rddbc260·270을 사용하는 후속 원장·잔액·회전일 서비스에도 이 문자 비교를 적용한다. 원장별 조정할인 포함 여부와 방향 분류는 별개의 규칙이다.

- Rddbc310 등록 시 Rddbc260·270 동시 집계. Rddbc130 매출/매입 발생도 양쪽에 각각 00/50 코드로 장부/실금액 집계.
- 00/50은 Receive_Amt=0, Supply_Price/Tax_Price에 금액 저장. 기타 코드는 Receive_Amt에 금액, 공급가액/세액=0.
- 32/82는 장부 및 실잔액 양쪽에 반영. 제공된 장부매출원장 SQL에서는 32 제외; 우선 그대로 적용. 매입원장의 82 제외 및 전체 할인 옵션은 추가 확인. 전체 잔액에서 일괄 제외하지 않는다.
- 후속 검토용 산식(구현·확정 아님): 이월잔액 + 매출(또는 매입)금액 - 입금(또는 출금)금액 - 어음금액 - 할인금액 ± 조정금액. 코드별 상호 배타적 분류 및 실제 저장 부호 확인으로 이중 차감 방지.
- 영업/회계입력: R310 Account_Flag, R320 Acount_Flag 0 영업, 1 회계. 잔액 포함 정책은 기존 ERP 확인.

## 5. 입출금·어음·담보 연계
R310 Note_No/Note_No_Seq = R320 Note_No/Note_No_Seq = R330 Note_No/Note_Seq (각 테이블 접두사 적용). 어음 관련 입출금 코드 11,12,61,62,63. 매출처에서 받은 어음을 매입처 B에 담보 제공, 회수 후 매입처 C에 다시 제공할 수 있다. 같은 어음의 여러 담보 관계는 정상이며 거래처가 서로 달라도 연결된다. 거래처 동일 조건을 임의 추가하지 않는다. R330의 전체 PK를 보존하고 1:N 연결로 인해 R310 입출금액이나 R320 어음액이 중복되지 않게 별도 상세/후속 조회를 우선 검토한다. 빈 어음번호 연결 방지. 현재 보유/담보 상태 및 동일 거래처 재제공 이력은 실제 업무 확인 후 구현.

## 6. 원장·잔액 설계
- 장부매출원장 근거: `매출원장_거래명세서별.txt`. R120 거래명세서일 기준, Trans_Di='3', Io_Gu<'800', Fin_Supply_Price/Fin_Tax_Price 사용. R130은 전체 문서 키로 연결. R310 입출금일 기준, Receive_Di<'50' 및 <> '32', R320 어음번호/순번 연결. 이전 월 R260도 동일 구분 조건으로 UNION ALL. 이 SQL은 최종 잔액 산식을 보여주지 않으므로 실제 ERP 대조 필요.
- 매입원장: R110/R130/R310/R260·270 활용 제안. 실제 SQL 확보 후 조건 확정. 실원장도 별도 확인.
- 조회 시작월 이전 월집계 + 시작월 1일부터 조회 시작일 전일까지 상세로 이월 구성, 조회기간 상세 연결 제안. 완료월 잔액은 월집계 우선, 월중 기준일은 해당 월 상세 검토. 같은 기간 월집계와 상세 중복 금지. 현재잔액의 자료원은 갱신 특성 및 ERP 대조로 결정.
- 장부/실 잔액 및 원장 합계는 각각 별도 정의. 어음·담보 금액 자체를 입출금에 중복 합산하지 않는다.

## 7. 공통 구현 및 NLQ
기존 회사별 연결/권한, ERP Feature Registry, 바인딩 SELECT, 날짜/거래처/업무코드/사용자 검색, 표 formatter, 전체 다운로드, 채팅 게시/저장, Current Table, verified facts를 재사용한다. 신규 서비스 명칭은 기존 규칙에 따라 결정. 입출금과 입출고 의도 구분, KPIS 라우팅 보호. 기존 표로 처리 가능한 후속질문은 source_call_count=0. 금액 계산은 SQL/Python Decimal 또는 정확한 정수 사용, LLM은 설명만. 조회상한과 전체 범위를 명시하고 부분자료를 전체 잔액으로 표현하지 않는다. 회사·사용자별 캐시 및 결과 격리, 미인가 조회 DB 0회. 조회 권한은 아래 7.1절의 확정 정책에 따라 기존 IO_READ를 재사용한다.

후속 단계의 원천 NLQ 예: 오늘 입출금 조회, 다음 달 만기 어음. L2-1에서 구현한 현재표 후속질문과 구분한다. 월집계 테이블 자체는 독립 NLQ로 등록하지 않는다.

### 7.1 L2-1 승인 권한 정책 (2026-11-26)
- 최신 사용자 확정 지시에 따라 입출금·어음·담보 3개 조회는 기존 `IO_READ`를 공통 재사용한다. 기존 IO_READ 사용자는 별도 권한 부여 없이 조회한다.
- `FINANCE_READ`, `PAYMENT_READ` 등 별도 권한을 신설하지 않는다. 이전 금융 전용 권한 설계와 등록 도구는 폐기하며 실제 DB 등록/역할 변경은 수행하지 않았다.
- Excel/CSV 다운로드는 기존 조회 권한 `IO_READ`와 기존 `EXPORT_EXCEL`을 확인한다.
- 기존 로그인, 회사 접근 권한, 활성 사용자 검증, 회사·사용자·세션 격리를 그대로 유지한다. 기존 권한 테이블/역할/사용자 배정을 변경하거나 권한을 자동 부여하지 않는다.
- 입출금 관련 별도 권한관리는 향후 사용자가 요청할 때 별도 개발한다. 이번 작업에는 권한 등록·이관 절차가 필요하지 않다.
- L2-1은 패널 3개 조회·전체 다운로드·검증된 현재표 검색/집계까지 1호기 수동 합격했다. 신규 원천 NLQ 및 원장·잔액 계산은 후속 범위다.
- 일반 기본기간은 전월 같은 일부터 오늘까지다. 사용자가 지정한 기간을 유지한다. 상태/삭제/마감/영업회계 필터는 명시한 조건만 적용한다.
- 18자리 정수 금액은 Decimal로 수신한다. Excel의 15자리 정밀도를 넘는 값은 텍스트 셀로 보존한다. 화면용 천 단위 표시는 별도 복사본에서만 적용한다.

## 8. 실행 순서 및 Gate
| 단계 | 범위 | 상태 |
|---|---|---|
| L0 | 기존 프로그램 조사 | 완료 |
| L1 | ERP 자료 및 기본 업무 계약 | 기본 완료, 미확정 사항 별도 |
| L2 | L2-1 직접 조회 3종·현재표·다운로드, 이후 NLQ와 연계 조회 | L2-1 1호기 합격, 배포는 별도 승인 |
| L3 | 매입·매출원장 | 후속 |
| L4 | 거래처 잔액현황, 장부/실 비교 | 후속 |
| L5 | 수금·지급 추이, 회전일, 미수금, 여신·담보, 자금 Dashboard 및 예상 | 별도 협의 |

L2는 서비스/패널 기반과 NLQ/연계 검증을 단계적으로 진행. DB-free 테스트로 키, 조건, 정확 금액, 코드명, 중복, 권한, 결과 표시/다운로드 확인. NLQ 변경 시 전체 공식 NLQ 회귀, KPIS 보호 회귀 실시. 운영 DB 대조는 별도 승인된 최소 범위에서 수행. 1호기 수동 확인 후 사용자가 commit/push, 승인 후 2호기 배포/Smoke/Health 200.

## 9. 미확정 사항
특수 거래처 범위, 32/82 원장 옵션, 실제 매입·실원장 SQL, 저장 부호 및 조정 방향, 영업/회계 반영 범위, 어음 결제완료/분할어음 상태, 담보 만기 의미 및 회수완료/삭제/재제공 이력, 담보 제공·회수 잔액 반영 여부. 기본 조회는 확인된 원본 필드만 대상으로 하며 상태를 추정하지 않는다. 권한은 7.1절의 기존 IO_READ 재사용으로 확정되었고 신규 권한 등록/부여는 필요하지 않다.
