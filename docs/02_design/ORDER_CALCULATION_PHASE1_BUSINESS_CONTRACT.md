# 발주 계산 1차 업무 정의

- 버전: 1.3
- 기준일: 2026-09-14
- 기준 브랜치: `feat/dashboard-stock-extension-20260727`
- 검토 기준 HEAD: `acc0f5e3bf70b3b551749b79343ac1e35b6d171a`
- 성격: 후속 구현을 위한 공식 업무 정의. 현재 구현 완료 기능을 뜻하지 않는다.
- 상태: v1.3 적용 필요 영업일수와 결제일 당일의 다음 사이클 경계 확정. 남은 세부 업무질문은 제10절에 한정한다.
- 원칙: ERP SELECT only. ERP 발주 등록/확정, 자동발주, 운영 Snapshot 변경은 범위 밖이다.

## 1. 기능과 용어

| 기능 | 업무 의미 | 이번 정의/후속 1차 범위 |
|---|---|---|
| 발주 조회 | 이미 등록된 기존 발주자료 조회 | 기존 기능 유지 |
| 발주 계산 | 앞으로 발주할 제품과 추천수량 계산 | 대상 |
| 발주 작업 | 실제 ERP 발주 등록/확정 | 제외 |

`발주 보여줘`, `발주내역`, `발주현황`은 기존 발주 조회다. 후속 계산 action은 명시적인
`발주 계산`, `발주 추천`, `발주 수량 계산` 의도로 분리한다. 계산 결과에서 사용자가 결정하는 실제 발주수량도 ERP에
등록되었다는 의미는 아니다. 발주일자는 계산 기준일이며 실제 등록일과 구분한다.

본 문서의 공식 용어는 **안전재고**다. 사용자 설명의 안정재고는 같은 trigger 개념으로
해석하며, 현재고/실재고/장부재고와 혼동하지 않는다.

## 2. 입력과 영업일

| 입력 | 화면 기본값 | 의미 |
|---|---|---|
| 안전재고일수 | 3영업일 | 발주 필요 여부를 판정하는 최소 보유기간 |
| 적정재고일수 | 15영업일 | 발주 시 확보할 목표 보유기간 |
| 결제일자/마감일자 | 25일 | 당월 결제와 다음 결제 사이클의 경계일 |

세 값은 고정 정책 상수가 아니라 조회 시 사용자가 변경하는 조건이다. 결제일자는
월의 날짜이고 재고기간은 영업일수다. 결제일자 0은 현금/당일결제 거래조건을 뜻한다.
재고일수, 수요 환산, horizon은 모두 공식 영업일 Calendar를 사용한다.
Calendar가 없으면 평일/달력일을 임의 대체하지 않고 자료부족으로 표시한다.
현재고가 음수이면 그대로 사용하며 0으로 보정하지 않는다.

## 3. Trigger, horizon, 원 계산

안전재고는 발주를 할 것인지, 적정재고는 얼마까지 채울 것인지를 정한다.

```text
안전재고 기준수량 = 안전재고 영업일수에 해당하는 예상 필요수량
발주 trigger = 현재고 <= 안전재고 기준수량
계산 발주필요수량 = horizon 필요예정수량 - 현재고 - 입고예정수량
```

Trigger에는 현재고를 사용한다. 입고예정은 원 계산에서 차감한다. Trigger가 켜져도
계산값이 0 이하이면 발주 필요 없음이다. 음수 원 계산값을 발주수량으로 제출하지 않으며,
원 계산 근거와 발주 필요 없음 상태는 유지한다.

| 결제조건/시점 | 적용 필요 영업일수 |
|---|---|
| 결제일 이전 | min(적정재고일수, 기준일 다음 영업일부터 당월 말일까지의 실제 영업일수) |
| 결제일 당일 및 이후 | 적정재고일수 |
| 결제일자 0/현금 | 입력한 적정재고 영업일수. 월 마감 개념 미적용 |

월초에는 적정재고 기간까지, 월말에 가까워지면 당월 말까지 필요한 양만 확보한다.
마감 이후의 '한달치'라는 비공식 표현은 고정 1개월이 아니라 사용자가 입력한
적정재고 영업일수로 설명한다. 발주 계산에서는 결제일 당일부터 다음 발주 사이클로
본다. 현금이라는 이유로 horizon이나 수량을 강제로 1로 바꾸지 않는다.
적용 필요 영업일수는 공식 ssai_common_calendar의 기준일 다음 영업일 이후 날짜를
선택하여 센다. 기준일 자체는 제외하며 월 전체 영업일수에서 경과 일수를 빼서 결정하지 않는다.
화면의 공식 명칭은 '적용 필요 영업일수', '적용 필요예정수량'이다. 기존 horizon 필드는
호환용으로 같은 값을 보존하며 full result/current-table/download에서도 의미가 같다.
안전재고 0일/적정재고 1일/결제일자 0도 사용자 입력으로 허용한다.

예시 기본값 3/15/25, 해당월 22영업일에서 다음과 같이 설명한다.

- 월초: 현재고가 3영업일분 이하이면 15영업일 예정수량에서 현재고와 미입고를 차감.
- 마감 전, 월말까지 9영업일: trigger 충족 시 9영업일 예정수량에서 두 수량을 차감.
- 결제일 당일 및 이후: trigger 충족 시 15영업일 예정수량에서 두 수량을 차감.
- 현금결제: 사용자가 지정한 적정재고 영업일 예정수량에서 두 수량을 차감.

예시 수치와 날짜는 고정 코드로 사용하지 않는다.

## 4. 수요와 입고예정

수요 우선순위는 근거 있는 매출예정수량, 당월 정상출고 실적 기반 환산, 자료부족이다.
매출금액 예측을 수량 예측으로 간주하지 않는다.
품목별 추세와 예정수량은 기존 판매예측의 동일 기준기간/수량 계약을 사용한다.
추세 판단기간과 예측 산출기간을 별도로 고정하지 않고 기간과 원천 provenance를 함께 보존한다.

예측기반 수요는 기존 품목별 매출예상에서 최초 산출한 월 예상수량 자체를 유지한다.
당월 실제출고수량을 월 예상수량에서 차감하지 않는다. 실제출고는 이미 현재고에 반영되므로
이를 예정수량에서 다시 차감하면 실제 판매상태를 이중 반영한다.

```text
월 기준 예상수량 = 기존 품목별 매출예상의 월 예상수량
기준 1영업일 예상수량 = 월 기준 예상수량 / 해당 월 전체 영업일수
안전재고 기준수량 = 기준 1영업일 예상수량 * 안전재고 영업일수
horizon 필요예정수량 = 기준 1영업일 예상수량 * 적용 horizon 영업일수
원 계산 발주수량 = horizon 필요예정수량 - 현재고 - 입고예정수량
```

당월 실제출고는 추세/판매상태/설명용 근거로 보존하되 위 두 수요식 및 발주수량식에서
별도로 차감하지 않는다. 기존 Analytics의 잔여예상수량 지표 자체는 변경하지 않고
발주 계산만 월 예상수량과 월 전체 공식 영업일 Calendar를 사용한다.
발주 수요 horizon은 기준일의 다음 영업일부터 계산한다. 기준일 현재까지의 실제 매출/출고와
현재고는 이미 반영된 것으로 본다. 월간 잔여예상수량을 남은 영업일수로 나누는 구 계약은 폐기한다.
horizon이 차월로 넘어가면 차월 예측을 사용한다. 차월 예측이 없으면 당월 예측을 임의로
연장하지 않고 차월 수요 사용자 확인으로 처리한다. 별도 수요모델을 만들지 않는다.

예측이 없고 당월 정상출고가 있으면 다음 실적 페이스를 사용한다.
수요근거는 `실적기반`으로 구분하고 월초 pace에 임의 보정계수를 적용하지 않는다.
예측이 있으면 `예측기반`, 둘 다 없으면 `수요근거 없음`으로 표시한다.

```text
일평균 수요 = 당월 누적 정상출고수량 / 경과 영업일수
horizon 필요예정수량 = 일평균 수요 * 적용 horizon 영업일수
```

경과 영업일수가 0이거나 예측/정상출고 모두 없으면 임의 수요를 만들지 않는다.
반품을 정상출고 페이스에 임의 netting하지 않는다. 기존 Analytics의 broad IO 매출수량과
Snapshot 정상출고 수량은 동일 metric이 아니므로 원천/IO 조건을 기록한다.

입고예정은 R170/R180 기존 발주잔량 계약을 재사용한다.

| `Rd18_Or_Di` | 기존 미입고수량 |
|---|---|
| 1 | `Quantity + Oquantity` |
| 2 | `Quantity + Oquantity - In_Quantity` |
| 3 | 0 |
| 미정의 코드 | 상세 조회는 NULL. 제품합계의 기존 ELSE는 0이므로 품질 상태 별도 확인 |

신규 미입고 정의를 만들지 않는다. 제품합계 helper는 상세 원본의 표시 행수를 거치지 않는
제품 grain 집계다. 다만 기존 입고예정 기본 조회는 오늘 포함 최근 4영업일 발주만 대상으로
하므로 모든 미입고 발주를 포괄한다고 해석하지 않는다. 현재 화면의 '오늘 + 직전 3영업일'
관행은 오늘을 포함한 총 4개 영업일 날짜다. 기존 계약을 우선 재사용하며 3개 날짜로
축소하지 않는다. 발주 계산에서 이 최근 4영업일 범위만 유효 입고예정으로 사용하며,
오래된 발주는 계산용 미입고로 보지 않는다. 입고완료 상태는 제외하고 부분입고는
발주+할증-입고 잔량만 반영한다. 재고/잔량을 결과 grain에 연결할 때 중복 차감하지 않는다.
발주 계산은 저장된 재고위치와 함께 기존 `include_blank_stock_cd` 옵션으로 공백 재고위치
발주도 포함한다. 공백을 특정 창고로 변환하지 않고 포함 여부와 행수를 원천 정보로 보존한다.
제품별 입고예정 합계는 기존 발주처의 잔량 전체를 차감하며, 새 대표매입처가 과거 발주처와
다르다는 이유로 잔량을 제외하지 않는다. 다른 발주/입고예정 조회의 기본 필터는 변경하지 않는다.

## 5. 발주처와 단위

발주거래처는 대표 매입처다. 기존 SIMS inbound facts의 선정 로직을 재사용하고 별도
임의 선정 기준을 추가하지 않는다. 현재 구현은 설정된 대표 매입처 기간의 정상 양수입고를
후보로 하여 유상 `quantity` 합계, 공급가액, 최근 입고일, 거래처코드 순으로 동률을 해소한다.
양수 정상입고 후보 판정은 `quantity + oquantity > 0`이다. 실제 후보가 없으면 제품마스터
발주처로 보완하며 출처를 `actual_inbound`/`master_order_vendor`/`none`으로 보존한다.
기존 대표매입처 기본 조회범위 90달력일은 원천 선정기간이며 재고보유일수/horizon이 아니다.
이를 신규 '최근 1개월 발주단위 기간'과 혼동하지 않는다.

발주단위는 우선 최근 1개월 대표 매입처의 실제 발주이력으로 검토한다. 정상적인 반복단위를
신뢰할 수 없으면 발주단위 없음이다. 불규칙 발주 형태는 조달주의/사용자 확인으로 남긴다.

1차 이력기반 신뢰기준(2026-09-14): 기준일부터 역산한 최근 1개월 날짜 범위에서
같은 회사/제품/대표매입처의 정상 발주 상세를 사용한다. 완료 발주도 단위 이력에는 포함하되
미입고 산식의 완료 제외 계약은 그대로다. 수량은 할증을 제외한 실제 발주수량이다.
3개 이상 서로 다른 발주일, 관측 최소수량이 서로 다른 날짜에 2회 이상 반복,
모든 발주수량이 그 관측 최소수량의 양의 정수배인 경우만 단위를 채택한다.
최대공약수로 원천에 없는 단위를 만들지 않는다. 소수/비정상 수량, 이력 한도 도달,
상세 grain 중복, 반복 부족, 불규칙 수량은 단위 미확정 및 사용자 확인으로 둔다.
이는 등록된 공급업체 포장단위가 아니라 보수적으로 확인한 이력기반 추정 단위다.
당월 출고 거래처수는 기존 Analytics 정상출고 상세의 당월 제품별 distinct 거래처코드,
3개월 출고 거래처수는 승인 profile-exact Snapshot 통계를 재사용한다. 두 기간은 서로 다르다.
새 발주 계산 source budget에는 위 정상출고 상세와 발주이력 SELECT 각각 1회가 추가되며,
Snapshot generation 2-statement 및 Dashboard 3-call 계약에는 영향을 주지 않는다.
GCD, 최빈값 또는 최소수량 하나만으로 단위를 확정하지 않는다. 위 반복 발주 기준을
함께 충족해야 하며, 등록된 포장단위나 거래처의 공식 최소발주량으로 단정하지 않는다.

원 계산 후 추세가 **증가인 경우만** 단위 기준 올림, 나머지는 내림이다.
자료부족을 증가로 간주하지 않는다. 예: 원 계산 43, 단위 10이면 증가 50, 유지/감소 40.
추천 발주수량과 실제 발주수량은 소수 발주를 허용하지 않는 정수다.
발주단위가 있으면 증가만 단위 기준 올림, 유지/감소/자료부족은 단위 기준 내림이다.
단, 발주 trigger가 참이고 원 계산 발주수량이 양수인데 확정된 발주단위 내림 결과가
0이면 최소 발주단위 1회분을 추천한다. 예: 6.56/단위 10은 추천 10,
12.365/단위 100은 추천 100이다. 원 계산 Decimal 값은 보존하며 최소단위 적용을
계산근거에 표시한다. 발주 trigger가 거짓이거나 원 계산값이 0 이하이면 적용하지 않는다.
발주단위가 없으면 정수화 최소 단위 1로 계산하되 실제 발주단위를 추론하여 저장하지 않는다.
예: 원 계산 12.4는 증가 13, 그 외 12; 0.7은 증가 1, 그 외 0이다.
추천 0은 발주 필요 없음이다. 원 계산 Decimal과 horizon 수요 소수값은 근거 데이터에 보존한다.
단위 없음은 전체 계산 중단 사유가 아니다.
기존 추세의 신규/신규·증가 label을 단순 문자열 포함 검사로 증가에 합치지 않는다.
신규라는 이유만으로 올림하지 않는다. 실제 증가 근거가 있을 때만 올림한다.

## 6. 단가, VAT와 사용자 수정

발주단가 우선순위는 다음과 같다.

1. 지정 단가적용처의 발주일 기준 유효 계약단가. 미지정이면 코드 `50002`를 사용한다.
2. 계약단가가 없으면 대표 매입처 최종 매입가.
3. 그것도 없으면 제품 등록단가.
4. 모두 없으면 단가없음.

단가적용처가 지정되면 반드시 해당 계약을 먼저 확인한다. 적용금액과 출처, 기준일,
단가 basis, VAT 의미를 함께 보존한다.

미지정 단가적용처의 기본 코드는 `50002`, 미지정 재고적용처의 기본 코드는 `50001`이다.
사용자가 코드 또는 명칭을 직접 지정하면 지정값이 우선한다. 기본 코드는 이름 검색으로
선정하지 않으며, 회사별 코드명은 표시용으로만 읽는다. 회사에 코드가 없으면 임의 대체하지 않는다.
재고적용처 코드 조건은 기존 현재고 월누계 및 당월 입출고에 동일하게 전달한다.
Snapshot 평균매입단가는 최종 매입가나 계약단가의
대체물이 아니다. 재고적용처/단가적용처/대표매입처는 서로 다른 필드이며 코드/명칭/조건/
결과/계산 과정에서 제거하거나 합치지 않는다.

R070의 기존 lookup은 단가적용처+제품+기준일 key, 삭제/무효 후보 제외와 최신 유효행 선택을
재사용할 수 있다. 기존 `resolve_contract_price`는 선택 단가 0을 계약종료로 처리하며,
보험품 fallback도 포함한다. 그 fallback 전체를 이번 우선순위 대신 호출하면 안 된다.
계약종료 처리는 제10절 확인 사항이다. 조회조건에서 실/장부/OTC 종류를 선택하지 않는다.
기존 실입고 공급가 단가를 계약단가/최종매입가/등록단가의 자동 우선순위에 사용하며,
종료/무효 또는 복수 가격 충돌은 사용자 확인으로 구분한다.
대표매입처 최종 매입가에 복수행이 있고 기존 계약만으로 단일 유효값을 확정할 수 없으면
첫 행/MAX/평균을 임의 선택하지 않는다. 수량 계산은 유지하고 단가 사용자확인/금액 계산불가로
처리한다. 가격 충돌을 제품 등록단가 fallback으로 조용히 우회하지 않는다.

| 수량 | 의미 | 사용자 수정 |
|---|---|---|
| 계산 발주수량 | 원식의 발주필요수량 | 덮어쓰기 금지 |
| 추천 발주수량 | 추세/단위 적용 후 시스템 추천 | 덮어쓰기 금지 |
| 실제 발주수량 | 사용자가 결정한 값. 초기값은 추천수량 | 수정 가능 |

```text
발주공급가액 = 실제 발주수량 * 적용 발주단가(공급가)
발주세액 = 발주공급가액에 대한 표준 부가세
발주금액(부가세포함) = 발주공급가액 + 발주세액
```

사용자 수량 수정 시 실제수량 기준으로 공급가액/세액/포함금액을 즉시 다시 계산한다.
업무 승인 기준으로 모든 원 단가는 공급가 기준이며 대한민국 표준 부가세를 적용한다.
공급가 단가와 포함금액을 별도 컬럼으로 유지하여 VAT를 중복 적용하지 않는다.
기존 공통 금액 반올림 계약이 있으면 재사용하며, 없으면 반올림 단위/시점을 먼저 확정한다.
추천과 실제 수량 차이는 향후 업무 보정 근거로 유지한다. ERP write는 하지 않는다.

## 7. 조회조건과 결과

조회조건은 발주일자, 조회구분(전체/발주해당자료만/확인 필요), 안전재고일수, 적정재고일수,
결제일자, 발주담당자, 발주처 코드/명칭, 제약사 코드/명칭, 재고적용처 코드/명칭,
단가적용처 코드/명칭, 제품코드/제품명이다. 공통 제품 3조건은 제품그룹, 제품구분,
제품분류이며 기존 Gcode+Tcode/명칭 필터 의미를 그대로 재사용한다.
회사와 현재 저장 stock/product profile을 provenance로 보존하며 leading zero를 유지한다.
조회구분 전체에서도 자료부족/비대상 행을 숨겨서 정상값처럼 만들지 않는다.
확인 필요는 수요/재고 근거 부족, 적용단가 없음 또는 대표매입처 불명인 행을 조회한다.
사용자가 단가 종류를 선택하는 조회조건은 두지 않으며 기존 공급가 단가 계약과 제6절의
자동 우선순위로 결정한다. 주 결과표 하나에서 실제 발주수량을 수정하며 full 계산근거는
current-table과 다운로드에 보존한다. Panel은 제출 후에도 조건 수정/재조회용으로 유지한다.

결과 full schema에는 다음 항목을 유지한다.

| 구분 | 항목 |
|---|---|
| 식별 | 순서, 발주처 코드/명칭, 제품코드/제품명, 제조사, 재고적용처, 단가적용처 |
| 수량/금액 | 계산/추천/실제 발주수량, 재고수량, 입고예정수량, 발주단가(공급가), 공급가액, 세액, 발주금액(부가세포함) |
| 분석 | 매출거래처수, 매출수량, 이익기여등급, 품목이익등급, 출고빈도등급, 매입거래처수 |
| 계산근거 | 월 기준 예상수량, 수요근거, 월 전체/경과 영업일수, 기준 1영업일 예상수량, 발주단위, 추세, 단가출처, 안전재고일수/기준수량, 적정재고일수, 결제일자, 적용 필요 영업일수/적용 필요예정수량 |
| 감사/주의 | 당월 매출/정상출고수량, 최근 발주횟수, 조달주의, 발주사유, 상태, 기간/원천 provenance |

기본 요청의 발주수량은 실제 발주수량이다. 세 수량의 의미를 화면과 download에서 명시한다.
등급은 기존 Snapshot 명칭인 손익등급/기여도등급/출고빈도등급과 대응시킨다. 세 등급은 독립이다.
빈도 A에서 E는 상대적으로 낮아지는 순서이며 F는 최초 정상입고 M0~M2, X는 최근 완료
3개월 정상출고 없음이다. 손익/기여는 관리용 추정치이며 회계 확정손익이 아니다.
Snapshot에 존재하는 거래처수/매출수량은 해당 기간/실제 거래처 authority를 그대로 보존한다.
현재 Snapshot에 없는 매입거래처수의 집계기간만 제10절 질문으로 남긴다.

주요 열만 화면에 우선 표시해도 underlying full result/current-table/download에서 근거를
잃지 않는다. 200/300행 display limit는 계산 입력 limit가 아니다. R170/R180 상세 조회에는
별도 source TOP와 limit-hit metadata가 있으므로 bounded 상세 조회를 전체 이력으로
오인하지 않는다. source가 잘렸거나 completeness 미확인이면 전체 계산 완료로 보고하지 않는다.
사용자 수정값이 반영된 full result를 export하며 회사 변경 시 수정/cache/current-table을 격리한다.
결과 및 사용자 수정행 key는 회사+발주일자+대표매입처+제품이다. 같은 key는 단일 행이며
서로 다른 재고적용처/단가적용처 정보를 임의로 제거하거나 중복 합산하지 않는다.
Snapshot에 이미 존재하는 최근 완료 3개월 출고수량/실제 출고거래처수와 독립 등급은 재사용한다.
당월 수요용 실적과 이 통계의 기간을 혼동하지 않는다. 현재 schema 2.1에는 매입거래처수,
대표매입처, 추세/예측, 현재고, 계약단가가 없으므로 Snapshot에 존재한다고 가정하지 않는다.
Panel은 제출 1회에 결과/feedback 1회, rerun은 과거 payload를 재승격하지 않는 계약을 유지한다.

## 8. 자료부족와 설명가능성

예정수량/정상출고/추세 근거 없음, 단위 없음, 단가 없음, 대표 매입처 불명은 각각 별도 상태다.
숫자 0으로 모두 치환하지 않는다. 수요 없음은 계산불가, 단위 없음은 단위환산 불가,
단가 없음은 금액계산 불가로 구분하여 가능한 raw 값과 사용자 확인 근거를 유지한다.
단위 없음은 제5절의 최소 단위 1 정수화 추천, 단가 없음은 수량 유지/금액 계산불가,
수요 근거 없음과 대표매입처 불명은 사용자 확인으로 각각 처리한다.
하나의 자료부족 때문에 전체 계산을 HOLD하지 않는다. 다만 profile mismatch는 기존
fail-closed를 유지하며 다른 회사/범위의 Snapshot을 대체 사용하지 않는다.

제품별 사유는 실제 입력/계산값의 결정적 설명이다. LLM이 trigger나 수량 사유를 생성하지 않는다.
예: 안전재고 부족 / 현재고 2.1영업일 / 목표 15영업일 / horizon 9영업일 /
입고예정 100 / 증가추세 / 발주단위 50. 수요가 0/자료부족이면 보유일수도 임의 산출하지 않는다.

## 10. 남은 실제 업무질문

확정된 Q01(마감일 포함), Q04(기존 미입고 관행), Q06(증가 근거), Q09(단일 결과 grain),

확정됐으며, 아래에는 아직 공통 코드만으로 결정할 수 없는 세부 사항만 남긴다.

| 업무질문 | 이유 | 선택지 |
|---|---|---|
| 짧은 달의 29~31일 마감 입력은? | 실제 월에 존재하지 않는 마감 입력 처리 필요 | 유효 월말로 제한/입력 오류 |
| 계약 종료 0단가의 후속 처리 정책은? | R070은 종료와 부재를 구분함. 현재는 종료/무효 사용자확인 | 사용자확인 유지/별도 승인된 fallback |
| 공급가액/세액 반올림 단위와 시점은? | formatter는 표시 계약이며 정산 반올림 계약과 다름 | 기존 업무 money helper 확인 후 재사용/원 단위 및 세액 단계 별도 승인 |
| 동일 결과 key에 복수 재고적용처/단가적용처가 남으면? | 단일행 grain은 확정됐으나 적용처는 합치거나 제거할 수 없음 | 명시적 적용처 조건으로 단일화/충돌 필드 사용자확인 |
| Snapshot에 없는 매입거래처수의 집계기간은? | 현재 2.1 row에 해당 필드 없음 | 기존 inbound facts 기간/별도 승인 기간; 미확정 값은 자료부족 |

이 질문은 확정된 계산식이나 기능 전체를 다시 HOLD하는 사유가 아니다. 확정된 pure 계약과
공통 연결 설계는 시작할 수 있으며, 해당 미확정 세부 정책을 임의 기본값으로 구현하지 않는다.
현금결제 때문에 1영업일을 강제하는 규칙은 폐기됐다.

### 10.1 허용된 원천 연결 및 source budget

- 기존 대표매입처 선정 공통 authority는 `dashboard_inbound_facts_service.py`에 있다.
  Snapshot 관련 분석에서 사용하던 기준을 그대로 재사용하고 신규 선정 규칙을 만들지 않는다.
  frequency Snapshot row에는 대표매입처 자체가 저장되어 있지 않다는 구현 구분을 유지한다.
- Snapshot에 이미 있는 통계/등급은 재사용한다. 없는 현재고/예측/대표매입처/계약단가/
  발주이력 등은 기존 read-only 서비스 SELECT 재사용이 허용된다.
- 신규 발주계산의 source budget은 별도 계약으로 관리한다. 구현 설계에서 원천별 statement 수,
  timeout, retry=0, 실행시간 및 completeness를 명시하고 불필요한 호출을 최소화한다.
  화면/다운로드/current-table은 같은 full result를 재사용하며 동일 원천을 다시 조회하지 않는다.
- Snapshot generation R110 1회+R120 1회=2 statement, Dashboard source_call_count=3은
  변경하지 않는다. 신규 발주계산 source budget을 이 기존 예산에 섞지 않는다.
- R170/R180 상세 source TOP는 완전 이력으로 해석하지 않는다. 기존 미입고의
  오늘+직전 3영업일(총 4개 날짜) 관행과 잔량 산식을 유지하며 중복 차감하지 않는다.
- R230 복수 단가행에서 기존 계약으로 최종 매입가를 확정할 수 없으면 임의 선택 금지.
  수량 계산은 유지하고 단가 사용자확인/금액 계산불가로 처리한다. 이 충돌 처리 자체는
  확정됐으므로 추가 업무질문으로 남기지 않는다.
- ERP write/DDL, Snapshot schema/migration 변경과 실제 ERP 발주 등록은 허용하지 않는다.

## 11. 후속 구현과 합격 기준

### Excel과 화면의 동일 결과 계약

조회구분은 최종 표시/필터 조건이며 원천 조회와 수량 계산의 조건이 아니다.
전체에서 모든 대상의 계산을 수행하고 발주해당자료만은 같은 결과의 발주해당 행만 표시한다.
명시된 조회구분을 우선하며 내부 `only_needed`는 이에 맞춰 정규화한다.
회사 및 나머지 조회조건이 동일하고 조회구분만 변경된 경우 직전 원천자료를 재사용한다.
같은 조회구분으로 다시 제출하거나 다른 조회조건을 변경하면 새로운 원천 조회를 수행한다.
적용처 코드/명칭 4필드는 기본 조회조건 첫 줄에 배치하고 재고위치만 상세조건에 둔다.

Excel은 화면과 같은 full result를 사용하며 앞부분을 다음 순서로 둔다:
제품코드, 제품명, 규격, 추세, 계산 발주수량, 추천 발주수량, 실제 발주수량,
재고수량, 입고예정수량, 발주처, 발주단가, 발주금액(부가세포함),
월 기준 예상수량, 안전재고 기준수량, 적용 필요예정수량.
나머지 수요, 거래처수, 단위 근거, 적용처, 등급과 내부 계산근거는 뒤에 모두 보존한다.
단가 빈값의 확인 사유는 기존 `단가출처`를 그대로 제공하며 새로운 가격을 만들지 않는다.
화면의 계산 발주수량만 소수 2자리로 표시하고 원본 Decimal에 추가 반올림을 하지 않는다.
다운로드는 공통 export 경로의 숫자 셀, 코드 문자열과 leading zero, NULL 빈 셀 계약을 유지한다.
화면 300행 제한은 전체 다운로드에 적용하지 않으며 편집된 실제수량과 금액도 동일 원본에 반영한다.
기본 적용처 확인은 회사별 짧은 코드 조회를 사용하고 해당 계약단가는 기존 R070 서비스를 재사용한다.
이 조회는 발주계산 자체 source budget에 기록하며 Excel 생성이나 편집으로 재조회하지 않는다.

1. 확정된 본 문서 기준으로 1차 구현을 시작한다. 제10절 질문은 해당 세부 정책 구현 전에 확인한다.
2. DB 없이 trigger/horizon/수요/단위/단가선택/세 수량과 금액의 pure contract Gate를 만든다.
3. 기존 read-only service와 승인 Snapshot을 연결하되 원천 completeness와 회사격리를 검증한다.
4. 공통 Panel/NLQ/current-table/download 경로와 사용자 실제수량 편집을 연결한다.
5. 정상/음수 재고, 월초/월말/마감경계/현금, 휴일/Calendar 부재, 예측없음,
   단위없음/불규칙, 가격없음/종료계약/VAT, full/display limit와 회사전환을 회귀 검증한다.

합격은 같은 입력으로 결정적 수량/근거가 나오고 세 수량이 독립 유지되며, 실제수량 변경이
VAT 포함금액과 full export에 일관되게 반영되는 것이다. ERP 등록/확정은 하지 않는다.
기존 발주조회 라우팅과 Snapshot generation R110 1회+R120 1회, Dashboard source_call_count=3 계약을
변경하지 않는다. 신규 발주계산 조회의 자체 source budget은 구현 설계에서 별도 명시한다.

1차 목적은 추천->사용자 수정->실제 판매/재고 결과의 비교다. 계절품목은 사용자 판단을
유지하고, 축적된 결과로 안전/적정재고·예측·단위·조달·결제조건·Snapshot 사전저장 후보를
매월 보정한다. 이는 현재 자동학습이나 자동발주 기능을 뜻하지 않는다.
